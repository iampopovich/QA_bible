# Гайдлайн оформления статей QA_bible

Цель: все страницы книги выглядят и читаются одинаково, чтобы их было легко сверять, дополнять и
поддерживать. Эталон — раздел `avtomatizaciya-testirovaniya/` (переработан в PR #59).

Проверка: `python3 tools/style_lint.py` (сводка), `--page <файл>` (страница), `--rule S-xx`, `--worst N`.
ID правил ниже (S-xx) совпадают с ID в линтере. Шаблоны страниц — `docs/contributing/templates/`.
Связанные документы: [`freshness.md`](freshness.md) (актуальность), [`proofreading.md`](proofreading.md) (вычитка),
[`integrity.md`](integrity.md) (целостность книги и ссылки).

## 0. Принципы

1. **Копилка, а не учебник** (дисклеймер README): страница отвечает на один вопрос/термин, без воды.
2. **Структура важнее красоты**: настоящие заголовки → GitBook строит «On this page» и якоря для ссылок.
3. **Минимальный диф**: не переименовывать файлы и не менять слаги — это ломает URL сайта и внешние ссылки.
4. **Одна страница — один тип** (см. §1). Смешанные страницы делить.
5. **Источник у каждого утверждения**, которое не общеизвестно.

## 1. Типы страниц и шаблоны

| Тип | Где в основном | Шаблон |
|---|---|---|
| T — Теория (термин/понятие/вид тестирования) | obshee, vidy-metody-..., test-dizain, testovaya-dokumentaciya-..., sdlc-i-stlc, seti-i-okolo-nikh | `templates/theory-page.md` |
| I — Инструменты/практики (обзор фреймворков, AI-инструменты) | avtomatizaciya-testirovaniya, ai-v-testirovanii, mobilnoe-testirovanie/android | `templates/tools-page.md` |
| H — Как протестировать X (чек-листы, кейсы по доменам) | testirovanie-v-raznykh-sferakh-..., mobilnoe-testirovanie, prakticheskaya-chast | `templates/howto-page.md` |
| F — FAQ/карьера (авторский голос допустим) | faq-dlya-novichkov | T-шаблон без «Определения» |
| L — Подборка ссылок | poleznye-ssylki, `*/poleznye-ssylki.md` | §8.3 |
| R — README раздела | `*/README.md` | `templates/section-readme.md` |

Обязательный скелет любой страницы (кроме L):

```text
# Заголовок (English term)
<вводный абзац 1–3 предложения: что это и зачем QA>
## …смысловые секции…
## Источники
### Дополнительные материалы      (опционально)
```

## 2. Заголовки

* **S-01** Ровно один `# H1`, первой строкой файла.
* H1 теоретической страницы: `Русский термин (English Term)` — `# Подкожный тест (Subcutaneous Test)`.
  Названия продуктов/методологий без перевода: `# Vibe Coding`, `# Claude Code`.
  Вопросительная форма допустима только в FAQ (`# Как составить резюме?`).
* H1 может быть длиннее заголовка в `SUMMARY.md` (там короче) — это нормально, не синхронизировать насильно.
* **S-02** Сразу после H1 — вводный абзац (контекст/проблема), а не список, картинка, hint или определение-цитата.
* **S-03** Никаких псевдозаголовков `**Причины кратко**` / `**Что делать**:` отдельной строкой → `## Причины`.
  Жирный в начале пункта списка (`* **Smoke Testing** — …`) — это НЕ псевдозаголовок, допустимо.
* **S-04** Максимум `###`. `####` — только в длинных справочниках инструментов, и тогда лучше разбить страницу.
* **S-19** Страница > ~300 слов обязана иметь хотя бы один `##`.
* Заголовки — без точки и двоеточия в конце, с заглавной буквы, без жирного внутри.

## 3. Определения

* Первое упоминание термина: **жирным**, английский вариант в скобках: `**Flaky-тест (Flaky Test)** — тест, который …`.
* Секция `## Определение` — для T-страниц, когда определений несколько или есть официальное.
* **S-17** Официальное определение (ISTQB и др.) — цитатой с указанием источника, а не курсивом:

  ```markdown
  > **Функциональное тестирование (functional testing)** — тестирование, основанное на анализе
  > спецификации функциональности компонента или системы.
  > — ISTQB Glossary
  ```

  Список ISTQB-терминов (как в `obshee/defekty-i-oshibki.md`) — обычным списком `* **Ошибка (error)** — …`
  внутри одной цитаты или под фразой «Определения ISTQB:».
* Происхождение термина — одной фразой с автором и годом: «Термин ввёл Jimmy Bogard (2010)».

## 4. Списки

* **S-05** Маркер — `*` (так пишет редактор GitBook и большинство страниц). Не `-`.
* Вложенность — 2 пробела. Нумерованный список `1.` — только когда важен порядок (шаги, рейтинг) или нужна ссылка на пункт.
* **S-06** Пункты без `;` в конце. Короткий пункт (фраза) — без знака; пункт из полного предложения(-ий) — с точкой.
  В одном списке — единообразно.
* Пункт-определение: `* **Термин** — пояснение` (тире, не двоеточие).
* Списки ≤ ~15 пунктов; длиннее — группировать подзаголовками или таблицей.

## 5. Типографика и язык

* **S-07** Тире `—` между частями предложения (с пробелами). Дефис `-` — только внутри слов (`QA-инженер`),
  диапазоны — `–` или «от … до» (`10–20 раз`).
* **S-08** Кавычки — «ёлочки»; вложенные — „лапки“. Прямые `"` — только в коде.
* Буква **ё** — пишется в новом и переработанном тексте; массовая автозамена в старом не делается
  (риск ошибок), правится при переработке страницы.
* Английские термины: при первом упоминании — в скобках после русского; далее — как принято в индустрии
  (smoke, flaky, CI/CD без перевода). Названия продуктов — как у производителя (Playwright, GitHub Actions).
* Аббревиатура при первом упоминании раскрывается: `RCA (Root Cause Analysis, анализ первопричин)`.
* **Голос**: в T/I/H — безличный или «мы» команды; без «я», «на мой взгляд». Личный опыт автора — только в F (FAQ)
  или в hint-блоке «Из практики».
* **S-14** Хвосты Википедии убирать: сноски `[1]`, «(англ. Starting line)» → «(Starting line)».
* Числа: `10 000`, `90%`, `HTTP 200 OK`. Код, команды, имена файлов, заголовки HTTP — в `` `бэктиках` ``.

## 6. Ссылки

* **S-16** Внутренние — относительные, обязательно с `.md`: `[Тестирование push-уведомлений](../mobilnoe-testirovanie/testirovanie-push-uvedomlenii.md)`.
* **S-15** Никаких голых URL — всегда `[осмысленный текст](url)`, не «[тут](…)», «[ссылка](…)».
* `\_` в существующих GitBook-ссылках не трогать (работает); в новых — не добавлять.
* Ссылка на YouTube/доклад — с пометкой: `— доклад NDC, 40 мин`. Ссылка на t.me/telegra.ph — по возможности
  заменить на первоисточник (каналы исчезают).
* Новую страницу — связать: ссылка на неё из README раздела и минимум с одной соседней страницы.

## 7. Медиа, код, таблицы, hints

* **S-11** Картинки хранить в `.gitbook/assets/` (путь `../.gitbook/assets/имя.png`), не хотлинком
  (hsto.org, lh*.googleusercontent.com и т.п. со временем умирают).
  Имя файла осмысленное: `ws-burp-proxy-settings.png`, не `image (2).png`. Формат — PNG/WebP, ширина ≤ 1600px.
* **S-12** У картинки есть alt: `![Схема клиент-сервер](...)` или `<img src="..." alt="Схема клиент-сервер">`.
  Подпись — `<figcaption>` только если несёт смысл.
* **S-10** Блок кода — всегда с языком: `bash`, `yaml`, `json`, `typescript`, `python`, `java`, `http`, `gherkin`;
  схемы, ASCII-диаграммы и вывод консоли — `text`. Пример — минимальный, рабочий, с комментарием о главном.
* Таблица — для сравнений (инструмент × свойство, X vs Y). Не для длинного текста; ячейка ≤ ~20 слов.
* **S-20** Hint-блоки: `{% hint style="info" %}` — полезное замечание/из практики, `warning` — риски и частые ошибки.
  Не больше 3 на страницу.
* **S-21** `success`/`danger` не использовать.
* **S-13** Горизонтальные разделители `---` / `***` между секциями не ставить — разделяют заголовки.

## 8. Источники и ссылки в конце

### 8.1 Формат (S-09, S-18)

```markdown
## Источники

* [Название статьи](https://…)
* [ISTQB Glossary: functional testing](https://glossary.istqb.org/…)

### Дополнительные материалы

* [Название](https://…) — чем полезно (одной фразой)
```

* Варианты «Источники:», «Источник: [..]», «Доп. материал:», «**Дополнительные материалы:**» → привести к шаблону.
* `## Связанные материалы` (внутренние ссылки) — опционально, перед `## Источники`.
* Битые ссылки — заменить на архив (`web.archive.org/web/…`) или удалить; не оставлять мёртвыми.

### 8.2 Источники для T-страниц обязательны; для H/F — по возможности.

### 8.3 Страницы-подборки (L)

* Группы — `##` по типу ресурса (Курсы, Книги, Каналы, Тренажёры…), внутри — алфавит или по значимости.
* Пункт: `* [Название](url) — что это, язык (RU/EN), бесплатно/платно`.
* PR вида «добавить ресурс X»: проверить, что ресурс живой, без рефералок, не дубль, и что попадает в нужную группу.

## 9. Актуальность

Кратко (подробно — [`freshness.md`](freshness.md)):

* Версии, модели, цены, статистика — помечать датой: «(на 11.2026)» или «по данным … 2025».
* Не фиксировать версию без необходимости (`Playwright` вместо `Playwright v1.44.0`), если пример от неё не зависит.
* Страницы-«снимки» (`poslednee-obnovlenie-android-ios-chto-novogo.md`) — ссылки на официальные release notes,
  а не пересказ.

## 10. Файлы и оглавление

* Новая страница: слаг — транслит заголовка в стиле GitBook (латиница, `-`), файл в папке раздела,
  строка в `SUMMARY.md` (иначе страница не публикуется), ссылка из README раздела.
* Существующие файлы не переименовывать и не перемещать без явной договорённости с владельцем.
* README раздела (тип R) — вводный абзац + `## Содержание раздела` со ссылками «— о чём» (эталон:
  `avtomatizaciya-testirovaniya/README.md`).

## 11. Чек-лист PR

* [ ] `python3 tools/check.py` — «ОК» (целостность без новых ошибок, изменённые страницы не хуже базовой линии)
* [ ] Для перерабатываемой страницы: `python3 tools/style_lint.py --page <файл>` — «OK» (или исключения объяснены в PR)
* [ ] Новая страница внесена в `SUMMARY.md` и README раздела
* [ ] Внешние ссылки изменённых страниц проверены: `python3 tools/links.py --changed` — нет `DEAD`
* [ ] Переформатирование и правка содержания — разными коммитами (коммит оформления начинается с `Оформление:`)
* [ ] Если содержание сверено с актуальными источниками — строка в `docs/contributing/reviewed.tsv`
* [ ] Один PR — один раздел (или ≤ ~10 страниц), чтобы владелец мог отревьюить
* [ ] После исправления долга обновлены базовые линии: `tools/style_lint.py --write-baseline`, `tools/integrity.py --write-known`

## 12. Принятые решения

Зафиксированы при введении гайдлайна (11.2026):

1. Маркер списков — `*` (раздел «AI в тестировании», написанный на `-`, переводится на `*`).
2. Пункты списков — без `;` в конце.
3. Официальные определения (ISTQB и др.) — цитатой `>` с указанием источника, а не курсивом.
4. Горизонтальные разделители `---` между секциями не используются.
5. Орфография проверяется вычиткой по `proofreading.md`; автоматического спеллчекера нет.
6. CI нет — все проверки запускаются локально скриптами из `tools/`.

## 13. План миграции (по фазам, каждая — серия PR по разделам)

| Фаза | Что | Правила | Риск | Как |
|---|---|---|---|---|
| 1. Механика | секции источников, маркеры `*`, язык у блоков кода, битые внутренние ссылки, разделители, success/danger-hints | S-05, S-09, S-10, S-13, S-16, S-21 | низкий | скрипт + вычитка дифа |
| 2. Структура | псевдозаголовки → `##`, вводный абзац, ISTQB-цитаты, `;` в списках | S-02, S-03, S-06, S-17, S-19 | средний | полуавтомат, вычитка каждой страницы |
| 3. Типографика | тире, «ёлочки», хвосты Википедии, голые URL | S-07, S-08, S-14, S-15 | средний (код, таблицы) | скрипт с исключением кода и URL |
| 4. Медиа | перенос внешних картинок в `.gitbook/assets`, alt-тексты | S-11, S-12 | низкий, но объёмный | скачать, осмысленно назвать |
| 5. Содержание | мёртвые ссылки (`tools/links.py`), устаревшие даты/версии (`tools/freshness.py`) | `freshness.md` | высокий | вручную, с источниками |

Порядок разделов — от худших по `python3 tools/style_lint.py` к лучшим. Текущее состояние всегда берётся из
вывода линтера, а не из этого документа.
